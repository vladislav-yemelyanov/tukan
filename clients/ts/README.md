# Tukan TypeScript Client (`tukan`)

Zero-dependency, schema-typed `fetch` HTTP client built for TypeScript types generated by Tukan (`Schemas` / `Schemas["Operations"]`).

## 1. Overview & Design Principles

Conforms to the shared Tukan HTTP client requirements matrix (`docs/client-requirements.md` in the Tukan repository).

- **Zero external dependencies:** Built purely on standard Web Fetch APIs (`fetch`, `Headers`, `FormData`, `URLSearchParams`, `AbortController`, `Blob`, `DOMException`). Built with TypeScript `strict` + `exactOptionalPropertyTypes` + `noUncheckedIndexedAccess`.
- **Zero-runtime coupling in `api.ts`:** Generated TypeScript files export pure type declarations (`Schemas` / `Schemas["Operations"]`) with zero runtime imports or client code.
- **Full OpenAPI operation typing:** `client.path(...)` constrains paths, HTTP methods, required/optional parameters (`path`, `query`, `headers`, `cookie`), discriminated media-type request bodies (`contentType` + `body`), success response types, and status-specific error bodies.
- **Strict non-throwing contract:** Every call resolves to `Promise<ClientResult<TData, TErrorMap>>`. Missing path parameters, network errors, timeouts, `AbortSignal` cancellations, malformed JSON responses, and exceptions inside hooks are all classified into a 7-variant discriminated `ClientError<TErrorMap>` union and routed through `onError` hooks.

## 2. Setup & Configuration

Install `tukan`:

```sh
npm install tukan
```

For local monorepo development against this repository, you can also point `package.json` to `"tukan": "file:../../clients/ts"`.

Generate your TypeScript API file(s) from `tukan.json5`:

```json5
{
  outputs: [
    { language: "ts", path: "./src/generated" },
  ],
  specs: [
    { name: "tasks", input: "./specs/tasks.json" },
  ],
}
```

### `createClient` & `ClientConfig`

```ts
import type { Schemas } from "./generated/tasks";
import { createClient } from "tukan";

const api = createClient<Schemas>({
  baseUrl: "https://api.example.com",
  timeoutMs: 10_000,
  headers: async () => ({
    Authorization: `Bearer ${await tokenStore.getAccessToken()}`,
  }),
});
```

| Field | Type | Default | Behavior |
|---|---|---|---|
| `baseUrl` | `string` | *(required)* | Trailing slashes are trimmed. Supports empty `""` or relative path prefixes (`"/proxy/"`). |
| `headers` | `HeadersProvider \| undefined` | `undefined` | Static `HeadersInit` / record, or sync/async `({ method, path, url }) => ...` provider run before each request. |
| `fetch` | `typeof fetch \| undefined` | `globalThis.fetch` wrapper | Custom fetch implementation for SSR, auth proxies, or unit tests. |
| `requestInit` | `FetchRequestOptions \| undefined` | `undefined` | Base `RequestInit` options (`credentials`, `cache`, `redirect`, `keepalive`, etc.) excluding `method`, `headers`, `body`, `signal`. |
| `timeoutMs` | `number \| undefined` | `undefined` | Client-wide request timeout in milliseconds (`<= 0` times out immediately), overridable per call via `timeoutMs`. |
| `onRequest` | `OnRequestHook \| readonly OnRequestHook[]` | `undefined` | Hook(s) run sequentially after body serialization; can mutate `context.url`, `context.headers`, `context.init`, and `context.extra`. |
| `onResponse` | `OnResponseHook \| readonly OnResponseHook[]` | `undefined` | Hook(s) run sequentially after transport returns; returning a `Response` replaces the active response. |
| `onError` | `OnErrorHook \| readonly OnErrorHook[]` | `undefined` | Hook(s) invoked sequentially on every `ClientError` before returning `{ data: undefined, error, response }`. |

If your OpenAPI document itself declares a schema named `"Operations"`, pass `Schemas["Operations_"]` (otherwise pass `Schemas` directly—`ExtractOperations<TSchema>` resolves `Schemas["Operations"]` automatically when keys start with `"/"`).

## 3. Type-Safe `client.path(...)` Usage

```ts
import { createClient, type Client, type ExtractOperations } from "tukan";
import type { Schemas as TasksSchemas } from "@/generated/tasks";

export type TasksClient = Client<ExtractOperations<TasksSchemas>>;

export function createTasksService(client: TasksClient) {
  return {
    list: (query?: TasksSchemas["ListTasksQueryParameters"]) =>
      client.path("/api/v1/tasks").get({ query }),

    getById: (taskId: string) =>
      client.path("/api/v1/tasks/{taskId}").get({ path: { taskId } }),

    update: (taskId: string, body: TasksSchemas["UpdateTaskRequest"]) =>
      client.path("/api/v1/tasks/{taskId}").patch({ path: { taskId }, body }),
  };
}
```

### Parameter & `exactOptionalPropertyTypes` Ergonomics

Optional properties inside `query`, `cookie`, and `headers` parameter objects automatically permit explicit `undefined` values (`AllowUndefinedOptional`), so callers using `exactOptionalPropertyTypes: true` can pass UI state like `{ status: statusFilter || undefined }` directly without manual conditional object spreads. Required fields in `path`, `query`, `headers`, `cookie`, and `body` remain strictly required.

### Per-Call `RequestOptions`

All operations support per-request options alongside any required OpenAPI slices:

```ts
const result = await client.path("/api/v1/tasks").get({
  query: { status: "todo" },
  headers: { "X-Trace": "custom" },
  cookie: { session: "abc" },
  signal: abortController.signal,
  timeoutMs: 3_000,
  requestInit: { cache: "no-store", credentials: "include" },
  extra: { attempt: 1 },
});
```

- `options.extra` is shallow-copied into `context.extra` so hook mutations never affect caller objects.
- Browser `fetch` forbids manually setting a `Cookie` header; in browser apps pass `requestInit: { credentials: "include" }` instead of `options.cookie`.

## 4. Result Model & Categorized Error Matrix

### `ClientResult<TData, TErrorMap>`

Every request returns a discriminated union:

- Success: `{ data: TData; error: undefined; response: Response }`
- Failure: `{ data: undefined; error: ClientError<TErrorMap>; response: Response | undefined }`

Checking `if (result.error)` narrows `result.error` to `ClientError<TErrorMap>`, and in the remaining branch `result.data` is `TData` and `result.response` is guaranteed to be a `Response`.

### Base `ApiError<TMap>` Members

All 7 error classes extend `abstract class ApiError<TMap> extends Error` and share:

- `readonly kind: ApiErrorKind` — discriminator (`"response" | "unexpected_http" | "network" | "timeout" | "cancelled" | "decode" | "client"`)
- `readonly message: string`
- `readonly status: number | undefined`
- `readonly body: ErrorMapBody<TMap> | undefined`
- `readonly rawBody: unknown`
- `readonly response: Response | undefined`
- `readonly cause: unknown`
- `isStatus(code: number): boolean` — runtime `status === code`
- `get isNetworkError(): boolean` / `get isTimeout(): boolean` / `get isCancelled(): boolean`
- `is<TStatus>(status: TStatus)` — type guard that narrows `kind` to `"response"`, `status` to `TStatus`, `response` to `Response`, and `body` to the OpenAPI schema declared for that status code (rejecting undeclared status codes at compile time).

### The 7 Error Categories (`ClientError<TMap>`)

| Class (`kind`) | Trigger | Narrowed Fields | `body` | Safe to Retry? | Recommended App Handling |
|---|---|---|---|---|---|
| `ApiResponseError` (`"response"`) | Non-2xx HTTP response whose body parsed cleanly (`error.is(status)` narrows per-status schema). | `status: number`, `response: Response`, `rawBody: unknown` | `ErrorMapBody<TMap> \| undefined` | No *(except 401 refresh)* | Show API `message`, map `fieldErrors`, or trigger login. |
| `UnexpectedHttpError` (`"unexpected_http"`) | Non-2xx HTTP response with malformed JSON payload. | `status: number`, `response: Response`, `rawBody: unknown`, `cause: unknown` | `undefined` | Only idempotent reads on `5xx`/`429` | Generic server error banner + log `status`/`rawBody` to telemetry. |
| `NetworkError` (`"network"`) | `fetch` transport threw before receiving a response (offline, DNS, TLS, connection reset). | `status: undefined`, `response: undefined`, `cause: unknown` | `undefined` | Yes (with backoff) | "No connection" banner + Retry action. |
| `TimeoutError` (`"timeout"`) | Exceeded `timeoutMs` / `ClientConfig.timeoutMs` (including `timeoutMs <= 0`). | `timeoutMs: number \| undefined`, `status: undefined`, `response: undefined`, `cause: unknown` | `undefined` | For reads / idempotent ops | "Request timed out" banner + Retry. |
| `CancelledError` (`"cancelled"`) | Caller aborted via `AbortSignal`. | `reason: unknown`, `status: undefined`, `response: undefined`, `cause: unknown` | `undefined` | No | Ignore silently in UI (navigation away, debounced search). |
| `DecodeError` (`"decode"`) | Server returned `2xx`, but JSON parsing failed (`SyntaxError`). | `status: number`, `response: Response`, `rawBody: unknown`, `cause: unknown` | `undefined` | **Dangerous for writes!** *(Server may have committed.)* | Generic failure message + log `cause` and `rawBody` to telemetry. |
| `UnexpectedClientError` (`"client"`) | Request build error (`stage: "request_build"`), throwing hook (`stage: "hook"`), or response stream failure / internal error (`stage: "internal"`). | `stage: ClientErrorStage`, `status: number \| undefined`, `response: Response \| undefined`, `cause: unknown` | `undefined` | No *(fix caller/hook bug)* | Log `stage` and `cause` to telemetry; show generic error UI. |

### Narrowing Patterns

**1. Concise UI handling + `error.is(status)`:**

```ts
const { data, error } = await services.tasks.create({ title });
if (error) {
  if (error.is(400) && error.body) {
    setFieldErrors(error.body.fieldErrors);
    setNotice(error.body.message);
    return;
  }
  setNotice(error.body?.message ?? error.message);
  return;
}
```

**2. Checking single error shape without repeating casts:**

```ts
const { data, error } = await services.tasks.getById(taskId);
if (error) {
  setNotice(error.body?.message ?? error.message);
  return;
}
```

**3. Exhaustive category handling via `switch (error.kind)`:**

```ts
if (error) {
  switch (error.kind) {
    case "cancelled":
      return;
    case "network":
    case "timeout":
      showRetryBanner("Connection issue. Please try again.");
      return;
    case "response":
      if (error.is(400) && error.body) {
        showFieldErrors(error.body.fieldErrors);
      } else {
        showErrorBanner(error.body?.message ?? error.message);
      }
      return;
    case "decode":
      telemetry.captureException(error.cause, { status: error.status, rawBody: error.rawBody });
      showErrorBanner("Unexpected server response format.");
      return;
    case "unexpected_http":
      showErrorBanner(`Server error (${error.status}).`);
      return;
    case "client":
      telemetry.captureException(error.cause, { stage: error.stage });
      showErrorBanner("Request could not be completed.");
      return;
  }
}
```

## 5. Request Serialization, Headers & Response Parsing

- **URL & query params:** Missing `{key}` path parameters fail immediately with `UnexpectedClientError(stage: "request_build")`. Query `null` and `undefined` values are skipped; arrays repeat keys (`?tags=a&tags=b`); `Date` serializes with `.toISOString()`; objects serialize via `JSON.stringify`.
- **Headers & cookies merge order:** `config.headers` (static or provider) → `options.headers` → `options.cookie`. Caller objects are never mutated.
- **Content-Type precedence:** Explicit `options.headers["Content-Type"]` > `options.contentType` > base `config.headers["Content-Type"]` > `"application/json"`.
  - When `body` is `FormData` or `contentType` is `"multipart/form-data"`, the client builds `FormData` (supporting `Blob`, arrays, scalars, JSON fields, skipping `null`/`undefined`) and deletes manual `content-type` so `fetch` generates the boundary.
  - `"application/x-www-form-urlencoded"` builds `URLSearchParams` (or forwards string/`URLSearchParams`).
  - `"application/json"` / `"application/*+json"` sends `JSON.stringify(body)`.
- **Response parsing:** `HEAD`, `204`/`205`/`304`, and `Content-Length: 0` return `undefined`. JSON responses (`application/json`, `application/*+json`) parse via `JSON.parse` (empty/whitespace returns `undefined`; parse failure yields `DecodeError` on `2xx` or `UnexpectedHttpError` on non-`2xx`). `text/*` or missing `Content-Type` returns `string | undefined`; other types return `Blob | undefined`.

## 6. Execution Pipeline, Hooks & 401 Refresh

1. Build URL (`stage: "request_build"`)
2. Resolve `config.headers` (sets `stage: "hook"` if `config.headers` is a function)
3. Build `Headers`, cookies, and body (`stage: "request_build"`)
4. Run `config.onRequest` hooks (`stage: "hook"`)
5. Send `transport(context.url, context.init)` with composed timeout/abort signal (`inTransport: true`)
6. Run `config.onResponse` hooks (`stage: "hook"`; returning a `Response` replaces it)
7. Parse response body and classify `2xx` / non-`2xx` errors
8. On any failure, run `config.onError` hooks (throwing hooks become `UnexpectedClientError(stage: "hook")`) and return `{ data: undefined, error, response }`

### Single-Flight 401 Refresh with `context.extra`

```ts
const refreshOnUnauthorized: OnResponseHook = async (context, response) => {
  if (response.status !== 401 || context.extra._retried === true) {
    return;
  }

  const refreshed = await runSingleFlightRefresh();
  if (!refreshed) return;

  context.extra._retried = true;
  context.headers.set("Authorization", `Bearer ${tokenStore.getAccessToken()}`);
  return transport(context.url, { ...context.init, headers: context.headers });
};
```

See end-to-end tests covering concurrent single-flight refresh, retry-once guards, and bounded retries in `test/client.test.ts`.

## 7. Cancellation & Timeouts

Pass an `AbortSignal` via `options.signal` and/or `timeoutMs`:

- If `signal` is already aborted when the request starts, it immediately resolves to `CancelledError` (preserving `signal.reason`), even if `timeoutMs <= 0`.
- If `timeoutMs <= 0` and the user signal is not aborted, the request times out immediately with `TimeoutError`.
- When both `signal` and positive `timeoutMs` are set, they compose via `AbortController` so whichever triggers first wins accurately (`CancelledError` vs `TimeoutError`).
